# 6. Database Overview — The File-Based Knowledge Store

Terrain has no database. Not a SQLite file hiding in the user's home directory, not a background server maintaining in-memory indexes, not an embedded key-value store. This was a deliberate architectural decision, not a shortcut taken during early prototyping that never got revisited. The entire knowledge layer — project indexes, generated documentation, agent context packs, freshness ledgers, session histories — lives as plain files on the filesystem. Understanding why this works, and why it works *well*, is key to understanding how Terrain thinks about knowledge.

## The intuition

Terrain sits at the intersection of two worlds: human-written code and machine-generated documentation. Its job is to read a codebase, understand its structure, and produce a layered knowledge store that both humans and AI agents can consume. The moment you commit to a traditional database, you introduce a set of assumptions that actively fight this mission.

A database requires a running process. That means installation, configuration, port allocation, and a lifetime to manage. For a tool that developers run locally against their own repositories, that's a heavy price. More fundamentally, a database creates a wall between the knowledge and the version control system that governs everything else in a developer's workflow. When your architecture docs live in a `.terrain/` directory inside a Git repository, they travel with the code. They appear in diffs. They merge in pull requests. They get reviewed. A database can do none of this.

The file-based approach also means agents — the AI coding assistants that Terrain is designed to orchestrate — can access knowledge without any intermediary. An agent with file-read and file-write primitives can load `agent/context.md`, search `agent/repomix.md` with grep, or inspect `.meta/freshness.json` to decide whether to trust what it's reading. There's no API to learn, no connection string to manage, no serialization boundary to cross. The filesystem *is* the API.

## The two tiers

Terrain's knowledge lives in two tiers: global configuration under `~/.terrain/` and per-repository knowledge under `{repo}/.terrain/`. The global tier is machine-local — it doesn't leave your machine, isn't versioned with any repo, and stores settings that are specific to your environment. The per-repo tier travels with the codebase and is where the substantive knowledge assets live.

### Global tier (`~/.terrain/`)

The global directory holds three things.

**Model and provider settings** live in `~/.terrain/settings.json`. This file persists which LLM provider is active, API keys, model names, endpoint URLs, and knowledge-refresh preferences. The settings system (implemented in `crates/terrain-core/src/settings.rs`) supports multiple provider profiles — OpenAI-compatible, Ollama, LM Studio — and keeps the active profile's fields synced into flat top-level keys for backward compatibility. The desktop app reads and writes this file directly; there's no settings database or preferences pane backed by a different store.

**Project registration** lives in `~/.terrain/registry.json`. This is a thin pointer file: a list of `{slug, repo_path}` entries that let the desktop app discover which repositories have been set up for knowledge indexing. When you run "add project" in the Terrain UI, it appends an entry here. When you remove one, it deletes the entry. The actual knowledge — the `index.md`, the agent packs, the Litho documentation — stays in the repository. The registry is just an index of where to find things. The implementation in `crates/terrain-core/src/registry.rs` caches the parsed file in memory and invalidates on write, keeping reads fast without any external caching layer.

**SDD session outputs** live under `~/.terrain/sdd/{slug}/`. Speculative Design Documents — the structured workflow where Terrain guides an AI agent through requirements, design, and implementation planning — produce artifacts that are tied to a session, not to the repository's knowledge store. These session outputs (phase documents, active session pointers) stay local because they're working material, not committed documentation. The session system in `crates/terrain-core/src/sessions/` manages creation, persistence, and cleanup of these transient workspaces.

### Per-repository tier (`{repo}/.terrain/`)

This is where the real knowledge lives, and it's where the architectural choice pays off most clearly. When Terrain scans a repository, it produces a layered structure of Markdown files and JSON metadata, all under `.terrain/`:

**The project index** (`index.md`) is the entry point — a machine-readable table of contents that describes the repository's structure, tech stack, and module layout. It's the first file an agent reads to orient itself.

**Agent-facing assets** live under `agent/`. The `context.md` file is a narrative architecture overview generated by an LLM — dense, structured, designed for consumption by coding agents that need to understand a codebase quickly. The `repomix.md` file is a compressed source-code index, a grep-able pack of the repository's actual implementation. Companion metadata (`meta.json`, `context-meta.json`) records when these assets were generated and from which baseline, so the freshness system can detect staleness.

**Human-facing documentation** lives under `human/`. These are Litho-generated docs — numbered, structured, designed for developers who want to understand the project without reading every source file. The `.meta/human.json` sidecar tracks generation provenance so Litho knows what's stale.

**Domain knowledge** lives under `knowledge/`. A project's glossary, internal API documentation, and domain-specific terminology live here. This is the private knowledge layer — maintained by the team, versioned with the repo, consulted by agents before they make claims about business logic.

**Metadata and synchronization** live under `.meta/`. The `sync.json` file tracks which git snapshot the knowledge was last synchronized against. The `freshness.json` file is the freshness ledger — more on this below.

**Transient workspaces** use `.litho-agent/` (for the Litho documentation generation process) and `.sdd-agent/` (legacy, migrated away). These directories are scratch space: intermediate results that are useful during generation but aren't part of the committed knowledge store.

## Why files work

The deeper reason files work for this use case is that Terrain's knowledge is *document-shaped*. The primary consumers are LLMs that read Markdown. The primary producers are LLMs that write Markdown. The primary access patterns are read-entire-file, grep-for-pattern, and write-new-version. These are the operations that the filesystem is optimized for — and that databases only approximate through abstraction layers.

Git handles the hard problems. Concurrent edits? Merge conflicts resolve the same way they do for source code. History? `git log` shows you every version of every doc. Access control? Same as the repository. Portability? Clone the repo, and the knowledge comes along. There's no data migration path to worry about because there's no schema to evolve — the "schema" is whatever structure the Markdown files happen to have.

And because everything is files, the system degrades gracefully. If Terrain isn't installed, the `.terrain/` directory still sits in the repo, readable by any tool that reads files. If the freshness ledger is missing, agents can still read the context docs — they just won't know how stale they are. If the registry is empty, `KnowledgePaths::from_workspace()` falls back to discovering the nearest Git root from the current working directory. Every dependency is soft.

## Freshness as soft consistency

A file-based store doesn't have transactions, write-ahead logs, or ACID guarantees. For knowledge assets that are generated from source code and meant to reflect its current state, this matters. Terrain's freshness tracking system (`crates/terrain-core/src/freshness/`) addresses this by treating staleness detection as a first-class concern rather than an afterthought.

The freshness ledger is a JSON file — `.meta/freshness.json` — that records a snapshot: the git HEAD at last computation, whether the working tree was dirty, a timestamp, and per-asset scores. When an agent or the desktop app wants to know whether the knowledge is trustworthy, it doesn't just read the ledger. It *validates* the ledger against the current git state. If HEAD has moved, if the dirty flag doesn't match, or if any companion metadata file has been modified since the ledger was written, the cached score is discarded and a fresh computation is triggered.

The scoring system produces a 0–100 score per asset, with thresholds that govern behavior. Above 80, the knowledge is considered fresh — agents can rely on it freely. Between 70 and 80, agents are warned to verify claims against the repomix source pack. Below 70, architecture-level context is considered untrustworthy. Below 50, agents should ignore the context docs entirely and read source code directly. This tiered trust model means the system never silently serves stale information — it either tells you the knowledge is good, or it tells you to look elsewhere.

Crucially, the freshness system is aware of knowledge-only commits. When you regenerate `.terrain/` assets and commit them, that advances git HEAD, but it shouldn't count as source drift. The scoring logic filters out commits that only touch knowledge output paths — `.terrain/`, `.litho-agent/`, `.sdd-agent/` — so that regenerating documentation doesn't penalize the freshness score.

## The path resolver

All path resolution flows through a single abstraction: `KnowledgePaths` in `crates/terrain-core/src/paths.rs`. This struct centralizes every path the system needs — from the global registry to per-repo agent packs, from SDD session workspaces to freshness ledgers. It resolves the workspace repository from the `TERRAIN_REPO_PATH` environment variable or by walking up from the current directory to find a `.git` root. Every other module in the system calls through `KnowledgePaths` rather than constructing paths independently, which means the path structure is defined in one place and can be reasoned about holistically.

This is the closest thing Terrain has to a schema definition. The "database structure" isn't described in a DDL statement or a migration file — it's described by the methods on `KnowledgePaths`: `project_index()`, `agent_pack_main()`, `freshness_meta_path()`, `sdd_sessions_dir()`. If you want to understand where a particular piece of data lives, you read this file. If you want to add a new category of knowledge asset, you add a method here and ensure `ensure_project_layout()` creates the directory.

---

The absence of a database isn't something Terrain works around. It's something Terrain works *with*. The filesystem gives you Git integration, agent accessibility, zero configuration, and graceful degradation — all properties that a database would either complicate or eliminate. The freshness system provides the consistency guarantees that matter, and `KnowledgePaths` provides the structural discipline. For a tool that generates knowledge from code and distributes it to both humans and machines, this turns out to be exactly the right trade.
