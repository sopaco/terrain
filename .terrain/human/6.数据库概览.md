# 数据库概览

---

## 本项目无传统数据库

Terrain 在架构上明确选择了「**文件系统即数据库**」方案，未使用 SQLite、PostgreSQL 或任何 ORM 框架。这不是疏忽，而是核心设计决策：知识资产需要随 Git 分支流转、被人类直接审阅和编辑，传统数据库反而增加了运维复杂度和版本控制难度。

如果你习惯了「所有数据都进数据库」的思维模型，可以把 `{repo}/.terrain/` 目录想象成一个**嵌入式文档数据库**——每个文件是一条记录，Git 是事务日志，而 `~/.terrain/registry.json` 是跨仓库的索引目录。

## 数据持久化方案

Terrain 的所有持久化数据都以 Markdown 或 JSON 文件形式存储。下表列出了主要存储位置及其用途。

| 存储位置 | 格式 | 内容 | 版本控制 |
|---------|------|------|---------|
| `{repo}/.terrain/human/` | Markdown | C4 架构文档（Litho 产出） | ✅ 随 Git 分支 |
| `{repo}/.terrain/agent/context.md` | Markdown | Agent 架构摘要（≤14KiB） | ✅ |
| `{repo}/.terrain/agent/repomix.md` | Markdown | 源码打包索引 | ✅ |
| `{repo}/.terrain/agent/meta.json` | JSON | 项目元数据 | ✅ |
| `{repo}/.terrain/.meta/sync.json` | JSON | 同步元数据（采集器、时间戳） | ✅ |
| `{repo}/.terrain/.meta/freshness.json` | JSON | 新鲜度账本 | ✅ |
| `~/.terrain/registry.json` | JSON | 项目 slug→repo 路径映射 | ❌ 本地全局 |
| `~/.terrain/sdd/{project}/sessions/` | Markdown | SDD 会话输出 | ❌ 本地临时 |
| `~/.terrain/settings.json` | JSON | LLM/ACP 配置 | ❌ 本地全局 |

## 为什么不用数据库

这个决策背后有三层考量：

**知识随代码走**——`.terrain/` 目录与源码在同一 Git 仓库中，PR 可以同时审查代码变更和知识资产变更。如果用中心数据库，知识更新与代码提交就脱钩了。

**人类可审阅**——C4 文档和 Agent 上下文都是 Markdown 格式，开发者可以直接在 IDE 中阅读和编辑，无需数据库客户端或管理后台。

**零运维**——不需要数据库安装、迁移、备份和连接池管理。对于一个小团队工具，这大大降低了部署门槛。

代价是跨项目的联合查询能力有限（只能通过 `terrain list` 和注册表遍历），但对于 Terrain 的使用场景——每个 Agent 通常只关注当前仓库——这是可接受的权衡。
