# 5. Boundaries & Interfaces

## 1. Opening

Terrain exposes three distinct interface surfaces: a **CLI** for scripted and interactive terminal workflows, a **Tauri IPC** bridge for the desktop GUI, and a **file-system convention** that both surfaces (and external tools) share. This document catalogs every external-facing command, IPC invocation, configuration key, environment variable, and integration protocol — the complete boundary between Terrain's internals and the outside world. Where an interface has a non-obvious design rationale, a *Design Intent* column explains why.

## 2. CLI Interface

The CLI binary is `terrain` (crate: `terrain-cli`). Commands are grouped by domain. Global flags apply to all commands.

### 2.1 Global Flags

| Flag | Type | Description | Design Intent |
|------|------|-------------|---------------|
| `--json` | bool | Emit machine-readable JSON output | Enables scriptability; GUI reads JSON from CLI subprocess |
| `--project <slug>` | string | Scope command to a specific project | Avoids repeating the project slug on every invocation |
| `--repo <path>` | string | Override repository path | Useful when the registry entry is stale or points to a moved repo |

## 4. Configuration

### 4.1 Settings File: `~/.terrain/settings.json`

The settings file is the single source of truth for all user-configurable behavior. It is loaded at app startup and on every `ask_knowledge` call; changes are persisted by `save_model_settings` and trigger a `ChatEngine` cache invalidation.

```json
{
  "provider": "openai",
  "model": "stepfun-ai/step-3.7-flash",
  "api_key": "sk-...",
  "base_url": "https://integrate.api.nvidia.com/v1",
  "ollama_host": "http://localhost:11434",
  "profiles": {
    "openai": { "model": "...", "api_key": "...", "base_url": "..." },
    "lmstudio": { "model": "qwen/qwen3.5-9b", "base_url": "http://localhost:1234/v1" },
    "ollama": { "model": "qwen3.5:9b", "ollama_host": "http://localhost:11434" }
  },
  "acp": {
    "binary": "opencode",
    "args": "acp",
    "command": null,
    "agent_execution": "acp",
    "auto_approve": true
  },
  "knowledge": {
    "incremental_refresh": true,
    "incremental_max_changed_files": 60,
    "incremental_human_docs": false
  },
  "language": "system"
}
```

### 4.2 Settings Schema

| Field | Type | Default | Description | Design Intent |
|-------|------|---------|-------------|---------------|
| `provider` | string | `"openai"` | Active LLM provider (`openai`, `lmstudio`, `ollama`) | Profiles enable switching without re-entering keys |
| `model` | string | Provider-dependent | Model identifier sent to the LLM API | Synced from the active profile on save |
| `api_key` | string | Provider-dependent | API authentication key | Never logged; stored in plaintext on disk |
| `base_url` | string | Provider-dependent | API base URL | Allows pointing to NVIDIA, local servers, etc. |
| `ollama_host` | string | `"http://localhost:11434"` | Ollama server address | Only used when `provider = "ollama"` |
| `profiles` | map | 3 built-in profiles | Named provider configurations | Enables A/B switching without data loss |
| `acp.binary` | string | `"opencode"` | ACP agent binary name | Resolved via PATH at runtime |
| `acp.args` | string | `"acp"` | Default arguments for ACP binary | `opencode acp` is the standard invocation |
| `acp.command` | string | `null` | Override full command string | Bypass binary + args when a wrapper is needed |
| `acp.agent_execution` | enum | `"acp"` | Execution mode: `"acp"` (pure ACP) or `"acp_native"` (native LLM) | Controls whether Ask delegates to OpenCode or runs directly |
| `acp.auto_approve` | bool | `true` | Auto-approve ACP tool calls | Reduces friction in non-interactive workflows |
| `knowledge.incremental_refresh` | bool | `true` | Use `git diff`-based updates instead of full regen | Saves LLM tokens on most commits |
| `knowledge.incremental_max_changed_files` | u32 | `60` | Max changed files before fallback to full regen | Beyond this, the diff is no longer a summary |
| `knowledge.incremental_human_docs` | bool | `false` | Include Litho docs in quick refresh | Disabled by default — Litho is the slowest stage |
| `language` | enum | `"system"` | UI/asset language (`system`, `zh_cn`, `en`) | `system` follows OS locale; affects doc filenames and tool descriptions |

### 4.3 Provider Defaults

| Provider | Default Model | Default Base URL | API Key Required |
|----------|--------------|------------------|-----------------|
| `openai` | `stepfun-ai/step-3.7-flash` | `https://integrate.api.nvidia.com/v1` | Yes (NVIDIA) |
| `lmstudio` | `qwen/qwen3.5-9b` | `http://localhost:1234/v1` | `lm-studio` (placeholder) |
| `ollama` | `qwen3.5:9b` | N/A (uses `ollama_host`) | No |

## 6. ACP Integration

ACP (Agent Communication Protocol) is Terrain's bridge to external coding agents. The primary implementation delegates to **OpenCode**, a standalone CLI binary that accepts structured prompts and returns Markdown artifacts.

### 6.1 Spawn Protocol

The ACP spawn command is resolved dynamically from settings:

```
{acp.binary} {acp.args}   →   opencode acp
```

When `acp.command` is set, it overrides the binary + args resolution entirely. The command is spawned as a child process via `tauri_plugin_shell` in the GUI, or via `std::process::Command` in the CLI.

### 6.2 Execution Modes

| Mode | Setting Value | Behavior |
|------|--------------|----------|
| Pure ACP | `agent_execution: "acp"` | All Ask queries and tool calls are delegated to OpenCode |
| ACP Native | `agent_execution: "acp_native"` | Native LLM for Ask; ACP only for Litho/SDD generation |

The mode is selected in `ChatEngine::with_settings` (`crates/terrain-agent/src/chat/mod.rs:73-104`): when `execution_uses_native_llm` returns true, a `NativeBackend` is built; otherwise, the engine expects `acp_available` to return true and delegates to `run_turn_acp`.

### 6.3 Litho Prompt Structure

When Terrain delegates Litho generation to ACP, the prompt includes:

1. **Skill directory** — path to the Litho skill's `SKILL.md` and references
2. **Repository root** — absolute path to the codebase
3. **Output directory** — where final `.terrain/human/` docs should be written
4. **Intermediate workspace** — where research artifacts are persisted
5. **Language directive** — target language for generated documents
6. **File listing** — expected output file names

**File reference:** `crates/terrain-core/src/assets/litho.rs:34-60` — `build_litho_generation_prompt`

### 6.4 ACP Availability Check

Before spawning, Terrain verifies:

1. The binary exists on `PATH` (or at the configured absolute path)
2. The binary responds to a version/help check
3. `acp_spawn_command` returns a valid command string

If the check fails, the system falls back to native LLM execution where possible, or returns a clear error to the user.

## 7. File System Conventions

### 7.1 Global State: `~/.terrain/`

| Path | Content | Lifecycle |
|------|---------|-----------|
| `settings.json` | User configuration | Persists across sessions |
| `registry.json` | Project registry (slug → repo_path mapping) | Updated on init/remove |
| `ask/<slug>/sessions/` | Ask session directories | Created per-session, pruned at 50 |
| `sdd/<slug>/sessions/` | SDD session directories | Created per-session |
| `bin/` | Agent tools (rtk, codegraph, terrain CLI) | Deployed by env integration |

### 7.2 Per-Project: `.terrain/`

| Path | Content | Generated By |
|------|---------|-------------|
| `scan/` | File index from GitScanner | `scan_project` |
| `agent/repomix.md` | Token-efficient codebase snapshot | `pack_agent_assets` |
| `agent/pack-meta.json` | Pack metadata (tokens, file count, tree) | `pack_agent_assets` |
| `agent/context.md` | LLM-generated architecture context | `run_agent_context_generation` |
| `agent/context-meta.json` | Context generation metadata | `run_agent_context_generation` |
| `human/*.md` | Litho human-facing documentation | `run_litho_generation` |
| `.meta/human.json` | Litho doc set sidecar (baseline, count) | `write_human_docs_meta` |
| `.meta/freshness.json` | Cached freshness scores | `compute_freshness` |
| `.meta/sync.json` | Last sync metadata | `pack_agent_assets` |
| `sdd/<session>/outputs/` | SDD phase artifacts | `save_sdd_output` |

### 7.3 Freshness Ledger: `.terrain/.meta/freshness.json`

The freshness ledger (`crates/terrain-core/src/freshness/ledger.rs`) is a versioned JSON document that records:

- **baseline** — Git HEAD at last computation, dirty state
- **assets** — per-asset freshness: `agent_pack`, `agent_context`, `human_docs`
- **drift** — commits since baseline, changed file count, sample of changed paths
- **summary** — overall score, stale flag, stale reason, drift factors

The ledger is consulted before recomputing: `resolve_freshness_summary` checks whether the ledger is still valid (HEAD matches, asset timestamps unchanged) and returns the cached summary if so.

**File reference:** `crates/terrain-core/src/freshness/compute.rs:30-250` — `compute_freshness` builds the full ledger

## 8. IPC Type System

All IPC payloads are defined in Rust and exported to TypeScript via `ts-rs`. The generated types live in `src/lib/generated/` and must never be hand-edited.

### 8.1 Export Workflow

1. Add or modify a struct/enum in Rust with `#[cfg_attr(feature = "ts-export", derive(ts_rs::TS))]`
2. Register the root type in `crates/terrain-ts-export/src/main.rs`
3. Run `bun run gen:types` (equivalent to `cargo run -p terrain-ts-export --bin export-ts-types`)
4. Run `bun run check` to verify TypeScript consumers compile

### 8.2 Type Mapping

| Rust Type | TypeScript Type | Notes |
|-----------|----------------|-------|
| `Option<T>` | `T \| null` | Not `undefined`; frontend must null-check |
| `Vec<T>` | `Array<T>` | Standard mapping |
| `String` | `string` | Always |
| `u64` / `u32` | `number` | With `#[ts(type = "number")]` annotation |
| `serde_json::Value` | `Record<string, unknown>` | For tool call arguments |
| `HashMap<String, T>` | `Record<string, T>` | Standard mapping |

**File reference:** `AGENTS.md` — IPC type conventions and modification workflow

## 9. Tool Interface (Ask Agent)

The Ask agent has access to a fixed set of tools, each with a defined contract:

| Tool | Parameters | Returns | Duplicate Protection |
|------|-----------|---------|---------------------|
| `search_knowledge` | `query, project?, limit?` | `{ hits: [...] }` | No (cheap) |
| `read_agent_context` | `project, section?` | `{ body, mode, section, freshness_warning }` | Yes (`context_call_fingerprint`) |
| `grep_agent_pack` | `project, pattern, context?, limit?` | `{ hits: [...], pack_path }` | Yes (`project:pattern` fingerprint) |
| `read_agent_pack_file` | `project, file_path, start_line?, end_line?` | `{ file, pack_path, hint? }` | Yes (`project:path:start-end` fingerprint) |
| `read_doc` | `path, project?` | `{ path, frontmatter, body }` | No |
| `list_projects` | (none) | `{ projects: [...] }` | No |
| `read_agent_pack_meta` | `project` | `{ meta, pack_path }` | Yes (`project` fingerprint) |
| `list_human_docs` | `project` | `{ documents: [...] }` | No |

Duplicate protection uses `tool_session_cache` (`crates/terrain-agent/src/tool_session_cache.rs`): within a single Ask session, identical `session_id:tool:fingerprint` combinations return the cached result flagged with `duplicate_call: true`, instructing the model not to repeat the call.

**File reference:** `crates/terrain-agent/src/tools.rs:295-352` — `grep_agent_pack_tool` with session cache integration
